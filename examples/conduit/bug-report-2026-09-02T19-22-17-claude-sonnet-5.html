high #1 Updating any profile setting without touching the password field silently wipes the account passwordSettings (update profile)
Endpoint: PUT /api/user
Steps to replicate
  1. 1) Register/login as a user (e.g. qauser2 / Passw0rd!).
  2. 2) Go to Settings, change only the Bio field (leave Password blank), click Update Settings.
  3. 3) Log out.
  4. 4) Try to log in again with the original password.
API calls
PUT /api/user -> 200, request body captured from the real browser request: {"user":{"bio":"QA tester bio update","email":"qauser2@test.com","image":"","password":"","username":"qauser2"}} (the Settings form always sends password:"" when the field is left blank)
POST /api/users/login {"user":{"email":"qauser2@test.com","password":"Passw0rd!"}} -> 422 {"errors":{"body":["Wrong email/password combination"]}}
POST /api/users/login {"user":{"email":"qauser2@test.com","password":""}} -> 200, login succeeds with an empty password
Separately: PUT /api/user with the password key omitted entirely from the body (e.g. {"user":{"bio":"x"}}) -> 500 {"errors":{"body":["data and salt arguments required"]}} (the update also fails outright when no password key is sent at all)
Expected

Saving Settings without entering a new password should leave the existing password unchanged, and the update should succeed either way.

Observed

After saving Settings with the password field left blank, the account's real password stops working (422 Wrong email/password combination) and an empty-string password now logs in (200). If the password key is left out of the request body altogether, the update crashes with a 500 instead.

high #2 Publishing an article with no tags crashes the server and leaves a corrupted, author-less article that breaks the global article list for everyoneCreate Article
Endpoint: POST /api/articles
Steps to replicate
  1. 1) Log in.
  2. 2) POST /api/articles with an article body that has no tagList key at all.
  3. 3) Reload the home page (Global Feed).
API calls
POST /api/articles {"article":{"title":"No Tags Article","description":"desc","body":"body text"}} -> 500 {"errors":{"body":["tagList is not iterable"]}}
sqlite3 dev.sqlite "SELECT id, slug, title, userId FROM Articles;" -> row 1|no-tags-article|No Tags Article|<NULL userId> — the Article row was inserted before the crash and never got an author
GET /api/articles?limit=3&&offset=0 (no filters, the Global Feed's own request) -> 500 {"errors":{"body":["toAppend.hasFollower is not a function"]}}
Expected

A request that fails validation should not create a partial database row, and one bad article should never take down the article listing for other users.

Observed

The create-article request crashes with a 500, but the article row is still written to the database with no author. Every subsequent load of the Global Feed (the site's home page) then crashes with a 500 as soon as it reaches that row, for every visitor, until the bad row is removed from the database.

  2. 2) Register a second account with username qauser1 again but a different email.
  3. 3) Separately: log in as a different existing user (qauser2) and use Settings to change their username to qauser1.
API calls
POST /api/users {"user":{"username":"qauser1","email":"qauser1b@test.com","password":"Passw0rd!"}} -> 201 (succeeds even though username qauser1 already exists on another account)
PUT /api/user (as qauser2) {"user":{"username":"qauser1","password":""}} -> 200 (renames qauser2 to the already-taken username qauser1)
sqlite3 dev.sqlite "SELECT id, username, email FROM Users;" -> 1|qauser1|qauser1@test.com, 2|qauser1|qauser2@test.com, 3|qauser1|qauser1b@test.com — three different accounts, one username
GET /api/profiles/qauser1 -> always returns account id 1's profile; accounts 2 and 3 become unreachable at /profile/qauser1
Expected

Signup and Settings should reject a username that is already in use by another account, the same way email already does.

Observed

Multiple accounts end up with the identical username. Profile lookups by username (GET /api/profiles/:username) always resolve to only the first matching account, so the other accounts' profile pages, and any article-author link pointing at them, silently show the wrong person's data.

Expected
